# dtcoder 9.9 尝鲜价套餐方案 — 代码评审报告

- **评审对象**：`local-docs/dtcoder-9.9-trial-plan.md`（223 行，7 个 Task）
- **评审阶段**：review（代码评审）
- **评审维度**：架构 / 业务逻辑 / 安全与风控 / 并发与幂等 / 测试覆盖 / 可观测性 / 合规与财务
- **评审结论**：⚠️ **Conditional Approve（有条件通过）** — 存在 3 个 Blocker 级与 7 个 Major 级问题，须在进入实现（Task 1）前澄清或补齐设计，否则资金安全与限购防薅存在实质性缺口。

---

## 1. 总体评价

计划整体结构清晰：背景目标 → 设计原则 → 套餐/权益/定价口径 → 7 个 Task（数据模型、风控、下单、权益限流、转化钩子、前端、埋点看板）→ 验收/风险/灰度。任务粒度合理、TDD 导向、灰度 5%→3 天→全量的节奏稳妥，回滚通过 `is_active=false` 下架入口且不影响存量 30 天有效期，方向正确。

主要缺陷集中在三类：
1. **资金与防薅的并发安全未落地**（限购去重无唯一约束/锁、支付回调无幂等）；
2. **关键业务口径自相矛盾或缺失**（"次月恢复正价" vs "到期降级免费版"、退款与限购的交互、灰度键稳定性）；
3. **合规与测试覆盖盲区**（设备指纹/支付哈希的个人信息合规、并发竞态与幂等用例缺失）。

## 2. 问题清单（按严重度）

### 🔴 Blocker（必须在实现前解决）

| # | 定位 | 问题 | 建议 |
|---|---|---|---|
| B1 | §2.1 设计原则1「三重去重」；Task 2 `trial_guard.py`；Task 1 `TrialPurchaseRecord` 字段 | 限购"每自然用户 1 次，账号+设备+支付方式三重去重"仅描述了校验逻辑，未指定**数据库唯一约束**或**分布式锁**。`check_purchase_eligibility` 检查与写入 `TrialPurchaseRecord` 之间存在 TOCTOU 窗口，高并发下黄牛可同时通过校验并各自写入，绕过限购。 | 在 `TrialPurchaseRecord` 上对 `(user_id)` 建唯一索引作为最终兜底；对 `(device_fingerprint)`、`(payment_method_hash)` 建唯一索引或预占表；校验+写入放同一事务，必要时引入分布式锁或 `INSERT ... | B2 | Task 3 `create_trial_order`「支付回调后开通」 | 支付回调可能重复到达，计划未提**幂等键**。重复回调会导致重复开通 `UserSubscription`、重复触发权益/埋点，甚至重复计费。 | 以 `order_id` + 支付渠道流水号作为幂等键，开通动作前查 `UserSubscription` 状态机（pending→paid→active），重复回调直接返回成功幂等响应；写入前用唯一约束兜底。 |
| B3 | §2.1 表「自动续费：到期降级免费版」 vs §1.1/§2「9.9 仅首月，次月恢复正价 99」 | 套餐定义为 30 天周期、默认不自动续费，则"次月恢复正价"与"到期降级免费版"**自相矛盾**：不续费即不存在"次月 99"。该口径直接影响价格展示、到期 cron、转化埋点分支。 | 统一口径：明确为"一次性 9.9 尝鲜 30 天 → 到期默认降级免费版（不自动续费）→ 用户主动续订则恢复 99/月"。划线价 99 仅作锚点展示，不代表自动续费价。修正 §1.1 与 §2.1 表述一致。 |

## 3. Task 级补充提示

- **Task 1（数据模型）**：`TrialPlan.entitlements`/`quota_limits` 用 JSON 存储，需定义 schema 版本字段以便后续灰度变更；`TrialPurchaseRecord` 唯一索引见 B1。
- **Task 2（风控）**：IP 限流建议在网关层（而非业务服务内）做，业务层只做账号/设备/支付去重，避免限流与下单耦合。
- **Task 3（下单）**：`UserSubscription` 需扩展 `source='trial'` 与状态机字段，便于到期 cron 与正价订阅区分；支付回调与开通须解耦（回调幂等入库 → 异步开通）。
- **Task 4（权益/限流）**：尝鲜版"旗舰模型限速"应改为"旗舰模型白名单"，明确尝鲜可用模型档位，避免高成本模型被白嫖（与 M6 一并处理）。
- **Task 5（转化钩子）**：券发放须幂等（按到期批次幂等键），避免 cron 重跑重复发券。
- **Task 6（前端）**：倒计时与"仅新用户可见"判定应来自后端接口返回，不要在前端硬编码可见性，防绕过。
- **Task 7（看板）**：埋点 schema 用 YAML 定义后，需与事件入库校验一致（字段名/类型），避免脏数据。

## 4. 合规与安全专项

- `device_fingerprint` + `payment_method_hash` 属个人信息/支付敏感数据，计划未提**个人信息保护法（PIIL/PIPL）合规**：需最小化采集、脱敏存储、用户授权、留存期限与删除策略。建议补一节"数据合规"。
- 支付方式哈希严禁存原值，采用单向哈希+盐；设备指纹采集前需在隐私政策中披露。
